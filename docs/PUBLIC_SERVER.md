# Публичный сервер Seatly

`node --import tsx server/hosted-index.ts` запускает интерфейс и API на одном origin. Сервер использует отдельную PostgreSQL через `DATABASE_URL`, проверяет TLS внешнего подключения и слушает `0.0.0.0:$PORT`. `SEATLY_PUBLIC_ORIGIN` должен содержать точный HTTPS origin без пути. Один доверенный обратный прокси завершает TLS.

При первом запуске оператор передаёт `SEATLY_BOOTSTRAP_ACCOUNTS`: JSON-массив объектов `name`, `email`, `role` (`guest` или `owner`) и индивидуальный `password` длиной 20–128 символов. Владелец обязателен до открытия порта. После создания аккаунтов удалите значение из окружения и выполните обычное развёртывание. Повторный запуск не меняет пароли существующих аккаунтов. Адреса опубликованных демо-аккаунтов запрещены. Пароли и токены не включайте в Git, URL или логи.

Сессия хранится в PostgreSQL как SHA-256-хеш случайного токена; cookie имеет Secure, HttpOnly и SameSite=Strict. Изменяющие запросы требуют точный Origin. Бюджеты входа и создания броней хранятся в общей БД и сохраняются после перезапуска. Выход отзывает сессию.

Каталог публичен. Гость получает только свои бронирования; владелец подтверждает ожидающие заявки. Цена и вместимость проверяются сервером. Повтор с ключом возвращает прежний результат. Транзакции сериализуют конкурирующие бронирования между экземплярами приложения; SQL-триггер повторно проверяет интервалы, даты и вместимость. Просроченные удержания освобождаются перед запросами и таймером каждые 30 секунд.

Локальный SQLite-сервер и его демо-аккаунты остаются отдельным режимом. Старый Sites/D1-адаптер сохранён в `hosting/`; публичный PostgreSQL-сервер не подменяет native identity того приложения.

Для обновления сохраняйте ту же DATABASE_URL. Схема и каталог инициализируются транзакционно; существующие бронирования, аккаунты и сессии сохраняются. Проверьте `/api/health`, вход, приватный список и подтверждение заявки после развёртывания. PostgreSQL не использует локальный таймер резервного копирования SQLite: резервирование и срок восстановления настраиваются у поставщика PostgreSQL. Перед работой с реальными данными проверьте отдельную копию и восстановление.

`tests/hosted-postgres.test.ts` проверяет два подключения к одной PostgreSQL, конкурирующие повторы, пересечение интервалов, права гостя/владельца, SQL-ограничения и сохранность сессии после переподключения. CI предоставляет отдельную PostgreSQL 17 через `SEATLY_TEST_DATABASE_URL`.
